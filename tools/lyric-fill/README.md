# 歌詞の補完（lyric-fill）— 試作・画面なし

First にだけ歌詞があり、Second・Third が空いているアカペラの MIDI に、**人が選んだパートと小節の範囲で** First の歌詞を写し、歌詞を書き足した `.mid` を作ります。設計の経緯は [Issue #22](https://github.com/daddyboubakiki-stack/Carapella/issues/22) を見てください。

- 状態：**試作**。処理部分と自動テストだけです。画面はありません。main には入れず、公開もしません
- カラモニ本体（`index.html`）は変えていません。読み込みの確認にだけ、`tests/extract.js` で `parseMidi` を取り出して使います
- 外部ライブラリなし。ブラウザ（`<script type="module">`）と Node のどちらでも、ビルドなしで動く書き方です

## 手元で試す（Node 18 以上）

```sh
node tools/lyric-fill/cli.js 曲.mid                                  # トラックの一覧
node tools/lyric-fill/cli.js 曲.mid --from 1 --to 2,3 --bars 1-16    # 写す候補と、写せない所（小節番号と理由）
node tools/lyric-fill/cli.js 曲.mid --from 1 --to 2,3 --out 曲_lyrics-draft.mid   # 書き出す
```

- `--from`（写す元）と `--to`（写す先）は、トラック番号か名前で指定します。どちらも省略できません（人が選ぶ前提）
- 入力ファイルは書き換えません。既にあるファイルにも上書きしません
- 書き出す前に、下の「書き出しの約束」を読み直して確かめます。守れていなければ保存しません
- 実際の曲の MIDI はリポジトリに入れないでください（著作権。テストは組み立てた MIDI と `tests/midi/` の合成MIDIだけを使います）

## 決まりごと

**対象にするファイル**：format 1、拍で数える時間（SMPTE でない）、壊れていない、カラオケ形式（.kar）でない。
**対象にするトラック**：1トラックに1チャンネル（打楽器の ch10 は数えない）。カラモニのパート名と同じ名前で表示します。

| 対象外 | 理由 |
|---|---|
| format 0、1トラックに複数チャンネル | 歌詞イベントはトラックに属し、チャンネルを持たない。カラモニは、同じ時刻に音がある最初のパートの歌詞として読む（Issue #22 の実験B） |
| .kar | カラモニは .kar のテキストイベントも歌詞として読むので、書き足すと二重になる |
| 途中で切れたファイル（ヘッダのトラック数より少ない、チャンクの長さが足りない） | 壊れたファイルを書き出しの元にしない |

**写す規則**：元パートの歌詞の tick と、先パートの音の始まりの tick が**ちょうど同じ**ときだけ写します。先パートに元から歌詞がある小節は、**丸ごと触りません**。tick が一致しても音楽的に正しい歌詞とは限らないので、最後はカラモニで確かめます。

**写し方**：歌詞を文字に直さず、元の歌詞イベント（FF 05）の**バイト列をそのまま**写します。Shift_JIS でも UTF-8 でも、元のまま残ります。先パートの、その tick で始まる音（note on）の直前に入れます。

### 自動で書けなかった所の理由

| コード | 報告の文 |
|---|---|
| `protected` | 先パートのこの小節には元から歌詞があるので、触らない（既存歌詞の保護） |
| `onset_mismatch` | 開始tickが違う（近く＝16分音符以内に音・歌詞があるが、ちょうど同じ位置ではない）。ずれの tick 数も出す |
| `target_sustain` | 先パートは前の音を伸ばしている（タイ・長い音） |
| `target_rest` | 先パートは休み |
| `source_no_lyric` | 元パートの音に歌詞がない（メリスマ・伸ばしの可能性） |
| `source_rest` | 元パートは休み |
| `source_multi` | 元パートの同じ位置に歌詞が複数ある |

報告は2つの向きで出します。「置けなかった元の歌詞」（小節・拍・歌詞・理由）と、「歌詞が入らない先パートの音」（小節・拍・理由）です。小節番号はカラモニの小節線と同じ数え方です。

### 書き出しの約束（`verifyOutput` で毎回確かめる）

1. ヘッダ・変えないトラック・未知のチャンクは、**バイト単位で同じ**
2. 変えたトラックは、書き足した歌詞を除くと、元のイベント列（tick・status・中身）と同じ
3. running status は元と同じ使い方。ただし歌詞を入れた直後の音だけは status を書く（SMF の決まりで、メタイベントの後は running status が切れるため）
4. delta のバイト列（冗長な書き方も含む）・End of Track の後ろのバイトも、元のまま
5. 書き足した歌詞は、指定したバイト列で、音の始まりの直前にある。同じ位置の重複はない
6. 元からある歌詞は変えない。同じ指定でもう一度実行しても、何も増えない

## 原本と編集を分ける

| | 中身 | 変更 |
|---|---|---|
| 原本 `readSong(bytes)` | 元ファイルのコピーから読んだ曲。`tracks[].lyrics` が原本の歌詞（バイト列・文字・小節・拍） | できない（凍結） |
| 編集 `planLyricFill(song, …).edits` | 原本に対する操作の一覧。今は `{ op: 'add', track, tick, bytes, text, from: { track, tick, lyricId } }` だけ | 新しい一覧を作って差し替える |
| 書き出し `applyEdits(song, edits)` | 原本のバイト列＋編集から新しい `.mid` | — |
| 見え方 `lyricsAfter(song, edits, track)` | 原本と編集を合わせた歌詞（将来のプレビュー用）。`origin: 'original' / 'copy'` | — |

将来、手で直す・譜割りを変える・「tun→とぅん」のように読みを変えるときは、`op`（たとえば `replace`）と、文字をバイト列にする方法を編集の側に足します。原本は変えません。今の `applyEdits` は `add` 以外を断ります。

## まだ確かめていないこと・限界

- 実際のアカペラ曲（編曲ソフトから書き出した MIDI）での一致の割合。tick がちょうど合う所がどれだけあるかで、この方法の役立ち方が決まる
- 小節線をまたぐメリスマ：既存歌詞の保護は小節単位なので、前の小節から続くメリスマの続きの音に、次の小節で歌詞が入ることがある
- 歌詞イベントが音の始まりから少しずれて置かれたファイルは、すべて「開始tick不一致」になる（自動では書かない）
- 小節番号は MIDI の拍子から数える（カラモニと同じ）。弱起などで楽譜の小節番号とずれることがある
- 写すのは歌詞イベント（FF 05）だけ。テキストイベント（FF 01）は写さない
- 先パートが和音を歌う場合は、和音の始まりに歌詞を1つだけ書く
- スマホのブラウザでの動作、書き出したファイルの保存・LINE での送受信、VoiSona での読み込み（どの文字コードを読めるか）
- 文字の手入力・読み変換・.kar・format 0 は対象外
